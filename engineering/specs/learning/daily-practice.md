# Daily practice and auditable review memory

Practice uses current school/subject/learner authorization, teacher-approved versioned questions bound to published topics, immutable own daily sets and server-verified answers. Downloaded work remains explicitly pending until its exact operation is synchronized and checked; it is never an official assessment mark. Practice evidence has a separate provenance adapter into mastery, so it cannot masquerade as released canonical marks. There are no peer rankings or counselling sources.

The deterministic memory engine uses the pinned official FSRS4Anki v4.5.0 reference at commit `8180871d9ef7e93943a60829533e46ab6d785ef4`, with the published 17 default parameters. Its MIT attribution is retained in `engineering/licenses/fsrs4anki-MIT.txt`. The scheduler stores its algorithm version with every transition. Reference vectors were generated from that immutable upstream JavaScript implementation with fuzz disabled, covering fresh memory, short/late reviews and same-day recall. These are numerical compatibility vectors, not learner outcome or provider-safety evaluations.

The application uses daily review granularity: again is due the next school-local calendar day instead of Anki's minute-step relearning. Intervals retain the FSRS rating ordering, with an explicit bounded maximum; a configured cap wins if adjacent intervals cannot fit. No random fuzz, paid inference or official-mark mutation occurs. The domain now binds approved questions to current published topic/term definitions and active published content readable by the learner. Immutable daily sets fit at most 600 estimated seconds. Exact operation receipts reauthorize current roles, ownership, modules and all set sources before replay. Reviews lock the owning actor, grade the first submitted answer against the immutable approved version, force an incorrect answer to Again regardless of self-rating, and update versioned FSRS memory. Late offline synchronization uses the server's school calendar day and accepts no client backdating; sets over seven days old are refused. Streaks count completed server-confirmed days with no ranking.

Downloaded approved answers and worked explanations are intentionally included for offline self-study. A learner can inspect them: practice is not a trusted examination or an official assessment mark. Only synchronized server-reviewed practice becomes a separately labelled mastery provenance. The subject aggregate mutex serializes evidence writes; when family mark visibility is off, the family projection reads practice-only records, never combined staff or raw question marks. Read-only requests do not synchronize derived topic nodes.

Teacher approval records immutable source/version identity and metadata-only audit receipts. Deactivation or source/publication withdrawal blocks later downloads and operation replay. Retained reviews and question versions cannot be silently rewritten; populated history refuses destructive rollback. The module defaults off and has no public routes in this domain increment. AI-assisted draft generation, typed API, learner/teacher screens and persistent offline client storage follow separately.


## Typed HTTP boundary

The additive practice endpoints expose scoped source/topic choices and the actual bank/set/review actions. Teacher source identity and academic scope are filtered before encrypted content metadata is loaded. Actor, current allocation or own approved learner, selected school, expected cookie account and published sources authorize again on receipt replay. Validation errors use the v2 envelope and never flash drafts into sessions. The shared private response wrapper covers authentication failures too.

The server returns its UTC time and school-day offline deadline together so clients can bound local leases without trusting an absolute device clock alone. Calendar fields remain YYYY-MM-DD strings in the generated SDK. The optional facilitator authoring flag is true only for a fresh eligible Teacher allocation and enabled module; absent older flags do not grant access.

## Persistent client operations

Student copies use a bounded encrypted store. Expired copies without pending answers are physically removed before the capacity check. Pending answers remain encrypted after expiry. The next storage access removes expired question bodies and worked explanations; an open foreground screen erases them at the lease deadline. Synchronization requires fresh current access and the original immutable operation.

Teacher approval persists its exact UUID, revision and submitted payload before any request. A dedicated encrypted approval store survives backgrounding and uncertain replies; the editor text is erased when the app becomes inactive. Recovery rechecks the original account, school, group, published topic and source before decoding or retrying that payload. A withdrawn source blocks the operation without silently replacing it. An unresolved operation has no automatic expiry, since forgetting it could produce a duplicate with a new UUID. The bounded store refuses additional operations instead of evicting unknown outcomes. Account/school replacement or explicit sign-out erases the corresponding key; a late old-scope cleanup cannot erase a replacement scope.

These encrypted web/Hive and synthetic HTTP checks do not establish physical-device keychain, screenshot, backup or live-school acceptance. AI-assisted question drafting remains a separate unfinished feature.
