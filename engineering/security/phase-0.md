# Phase 0 security record

Our checklist for Phase 0's security checks (the Build Bible, section 6, lists them), how each item is proven, and its status. The phase cannot close until every row is proven (the Build Bible, Appendix D). Each work stream fills in the rows it owns; the Test and Review roles confirm them at the gate.

Status values: **Proven** (evidence linked), **In place, not yet run** (built, waiting for an environment), **Open** (owned by another stream, not yet delivered here).

## Found at the Phase 0 close (S8)

| Finding | Evidence | Status |
| --- | --- | --- |
| The web portals cannot sign in from their own origin | Portal origins are Sanctum stateful domains (S6's `config/sanctum.php` default, and `SANCTUM_STATEFUL_DOMAINS` in `infra/gcp/env/*.env`), so every POST from a portal goes through the CSRF check: a portal built with `WEB_AUTH_MODE=bearer` gets 419 "CSRF token mismatch" on `POST /api/student/login`. The default cookie mode passes the check, but the sign-in endpoints issue a token and start no web session, so `GET /api/v2/me/context` with the session cookie answers 401. Checked locally against the merged phase branch on 2026-10-22 ([self-test record](../self-tests/phase-0.md), defect D1) | **Fixed** in S9 (`ea57571`, `9bb78db`): the panel's web group encrypted cookies twice, so the API could not read the session `/sanctum/csrf-cookie` started (the 419); a portal sign-in now logs the `web` guard in on a regenerated session and answers with an empty token (no bearer token in browser JavaScript), a refused one keeps no session, logout ends the session, and a password change elsewhere ends it (Sanctum's `AuthenticateSession`). `SESSION_DOMAIN=.navigateed.co.za` is applied with the portal stateful domains only once `APP_URL` is under it; otherwise the portals are built in bearer mode and only the panel is stateful. `Platform/PortalSignInTest` (CSRF enforced, unknown origins not stateful, phone apps unchanged); checked in Chromium ([self-test record](../self-tests/phase-0.md), S9 re-run) | |
| Pictures under `/storage` do not load in the web portals | The portals fetch avatars and subject pictures from the panel's `/storage` across origins; `/storage` sends no CORS headers (it is outside `config/cors.php`'s `api/*` paths and served as static files), so the browser blocks them (self-test defect D2) | **Fixed** in S9 (`dece88b`): Apache answers `GET`/`HEAD` under `/storage` from the CORS origins only with `Access-Control-Allow-Origin` (no credentials) and always sends `Vary: Origin` (`docker/storage-cors.conf`, origins from `config/cors.php` through `STORAGE_CORS_ORIGINS`); `server.php` does the same for `php artisan serve`. `Platform/StorageCorsTest`, `docker/tests/storage-cors.sh` (a real Apache, in CI) | |

## Restore procedure review — 23 October 2026

The old drill cut off outbound delivery after copying production data and used
`--min-instances=0` as if it stopped a worker. The corrected procedure requires
pre-copy quarantine: paused deployments/triggers, no running scheduler jobs,
removed revision tags, manual zero scaling on both services, and verification
that no instances or SQL consumers remain. Google documents manual zero scaling
and the independent tagged-revision exception. Restoration only resumes on demo
data after the copied-data inspection. The additional US$10/month cap applies
to disk changes and recovery artifacts as well as ongoing staging/mail.

Sanitisation clears queued/failed jobs, pending outbox intent, device/session
credentials and invitation authority before a private web-only inspection. The
array mailer discards bodies; the log mailer could expose them. Environment secret
overrides need independent checking. The cloud drill remains unrun: this is a
procedure correction, not evidence of runtime isolation or successful recovery.
