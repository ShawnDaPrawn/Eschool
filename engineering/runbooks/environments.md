# Environments

What runs where, how an environment is created, and what the product owner sets up once so the deploy workflows can run. All data stays in `africa-south1` (Johannesburg); Secret Manager keeps its secrets there too.

**Status.** Written in Phase 0. `infra/gcp/provision.sh` has been checked with `--dry-run` and shellcheck only; staging does not exist yet and production has not been changed. Every step below is waiting for its first real run, and the "Done" column of the setup checklist is empty until then.

## Overview

| | Local | CI | Staging | Production |
| --- | --- | --- | --- | --- |
| Where | Docker Compose (`docker-compose.yml`) | GitHub Actions (`ci.yml`) | GCP project `navigateed-staging` | GCP project `navigateed-d8c06` |
| Database | MySQL 8 container | MariaDB 10.11 service | Cloud SQL, own instance | Cloud SQL, own instance |
| Deployed | by hand | n/a | every merge to `main` (once enabled) | a `v*` tag, after a reviewer approves |
| Data | local seed data | wiped each run | seeded demo data; never real learners outside the restore drill | live schools |

The two cloud environments are separate projects, so the staging deployer has no access to production at all, and both use the same resource names.

## What exists per environment

| Piece | Staging (`navigateed-staging`) | Production (`navigateed-d8c06`) |
| --- | --- | --- |

The live instance is `db-f1-micro` on a 10 GB HDD until the first production run below |
| Database and user | `navigateed` / `navigateed` | `navigateed` / as on the live service (check before the first run) |
| Uploads bucket (mounted at `storage/app` in all three roles) | `gs://navigateed-staging-admin` | `gs://navigateed-d8c06-admin`, versioned: replaced or deleted files are kept 30 days |

| Service accounts | `navigateed-admin-run` (panel), `navigateed-worker-run` (worker and scheduler), `navigateed-scheduler-invoker` (Cloud Scheduler), `navigateed-deployer` (GitHub Actions) | same |

| Monitoring | uptime checks on `/login`, `/up` and `/up/worker` every 5 minutes; alerts for each check, errors above 20 in 5 minutes, any "Queued job failed" line, failing scheduler runs, and no worker instance for 10 minutes; Error Reporting | same, with the error threshold at 10 |

### Permissions (least privilege)

| Account | Can do | Granted on |
| --- | --- | --- |
| `navigateed-admin-run` | connect to Cloud SQL; read the app key, database password and admin password; read and write uploads | the project (`cloudsql.client`), each secret, the bucket (`storage.objectUser`) |
| `navigateed-worker-run` | the same minus the admin password, plus the SES secrets | the same |
| `navigateed-scheduler-invoker` | start the scheduler job | the job only (`run.invoker`) |
| `navigateed-deployer` | deploy revisions and update the job (`run.developer`), run them as the two runtime accounts (`iam.serviceAccountUser` on each), push images (`artifactregistry.writer` on the repository), take and read Cloud SQL backups (custom role `navigateedReleaseBackup`), deploy Hosting (`firebasehosting.admin`) | as listed; it can be impersonated only by GitHub Actions jobs running in this environment of `ShawnDaPrawn/Eschool` (Workload Identity Federation, no key) |

The container environment the script sets on all three roles: `CONTAINER_ROLE`, `APP_ENV=production`, `APP_DEBUG=false`, `APP_URL`, `LOG_CHANNEL=json`, `LOG_LEVEL`, `GOOGLE_CLOUD_PROJECT`, `DB_CONNECTION`, `DB_SOCKET` (`/cloudsql/<project>:africa-south1:navigateed-mysql`), `DB_DATABASE`, `DB_USERNAME`, `CACHE_DRIVER=database`, `SESSION_DRIVER=database`, `QUEUE_CONNECTION=database`, `TIMEZONE`, and where set `TRUSTED_HOSTS`, `SANCTUM_STATEFUL_DOMAINS`, `SESSION_COOKIE`, `ADMIN_EMAIL`. Secrets are mounted as `APP_KEY`, `DB_PASSWORD` and (panel only) `ADMIN_PASSWORD`. Staging runs `APP_ENV=production` on purpose, so it behaves exactly like production. See [wiki Configuration](../../wiki/Configuration.md) for each variable.

## One-time setup by the product owner

Do these in order. Commands assume Cloud Shell or a machine with `gcloud`, `jq`, `curl`, `openssl` and the Firebase CLI, signed in as a project owner.

| # | Step | Done |
| --- | --- | --- |
| 1 | Create the staging project and link billing | |
| 2 | Provision staging | |
| 3 | Add Firebase and the Hosting sites | |
| 4 | Configure GitHub: environments, variables, secrets, protection | |
| 5 | Turn on staging deploys and check the first one | |
| 6 | Switch on Error Reporting notifications | |
| 7 | First production run | |
| 8 | DNS and custom domains | |

### 1. Create the staging project

```bash
gcloud projects create navigateed-staging --name="NavigateEd staging"
gcloud billing projects link navigateed-staging --billing-account=<BILLING_ACCOUNT_ID>
```

If the id is taken, choose another and change `PROJECT_ID`, `FIREBASE_PROJECT_ID` and `BUCKET` in `infra/gcp/env/staging.env`.

### 2. Provision staging

```bash
ALERT_EMAIL=<address for alerts> infra/gcp/provision.sh staging --dry-run   # read what it will do
ALERT_EMAIL=<address for alerts> infra/gcp/provision.sh staging
```

The script prints the values for step 4 at the end. Cloud Run starts with Google's sample image; the first deploy replaces it. If an organisation policy blocks `allUsers` on the panel ("domain restricted sharing"), allow it for this project or the panel will answer 403.

Settings live in `infra/gcp/env/staging.env` (names, sizes, hostnames; never secret values). Change them there and re-run the script; it only creates what is missing and updates settings in place.

### 3. Firebase and Hosting sites

```bash
firebase projects:addfirebase navigateed-staging
firebase hosting:sites:create navigateed-staging-app --project navigateed-staging
firebase hosting:sites:create navigateed-staging-teach --project navigateed-staging
firebase hosting:sites:create navigateed-app --project navigateed-d8c06
firebase hosting:sites:create navigateed-teach --project navigateed-d8c06
```

Site ids are global; if one is taken, pick another and use it in step 4. The documentation site uses each project's default site. Register the staging Android, iOS and web apps for FCM and Crashlytics in `navigateed-d8c06` (one Firebase project, apps per environment, ADR 0003) when the app builds need them.

### 4. GitHub configuration

In the repository, **Settings > Environments**, create two environments:

| Environment | Protection | Deployment branches and tags |
| --- | --- | --- |
| `staging` | none | branch `main` |
| `production` | **Required reviewers**: the product owner; prevent self-review | tags matching `v*` |

Then add, per environment (**Settings > Environments > <name>**):

| Kind | Name | Staging value | Production value | Required |
| --- | --- | --- | --- | --- |
| Secret | `GCP_WIF_PROVIDER` | `projects/<staging project number>/locations/global/workloadIdentityPools/github/providers/github-actions` | the same with production's project number | yes |
| Secret | `GCP_DEPLOY_SA` | `navigateed-deployer@navigateed-staging.iam.gserviceaccount.com` | `navigateed-deployer@navigateed-d8c06.iam.gserviceaccount.com` | yes |
| Variable | `GCP_PROJECT_ID` | `navigateed-staging` | `navigateed-d8c06` | yes |
| Variable | `FIREBASE_SITE_APP` | `navigateed-staging-app` | `navigateed-app` | once `firebase.json` has an `app` target |
| Variable | `FIREBASE_SITE_TEACH` | `navigateed-staging-teach` | `navigateed-teach` | once `firebase.json` has a `teach` target |
| Variable | `FIREBASE_SITE_DOCS` | `navigateed-staging` | `navigateed-d8c06` | only if `firebase.json` gives the docs a `docs` target |
| Variable | `PANEL_URL` | `https://staging-admin.navigateed.co.za` once DNS works | `https://admin.navigateed.co.za` once DNS works | no (default: the service's `run.app` address) |
| Variable | `API_BASE_URL` | the API address compiled into the web portals | same | no (default: `PANEL_URL`) |
| Variable | `APP_PORTAL_URL`, `TEACH_PORTAL_URL` | portal addresses to smoke-test | same | no |
| Variable | `GCP_REGION`, `FIREBASE_PROJECT_ID`, `GCP_ARTIFACT_REPOSITORY`, `GCP_SQL_INSTANCE` | only if different from `africa-south1`, `GCP_PROJECT_ID`, `navigateed`, `navigateed-mysql` | same | no |

The two "secrets" are identifiers, not credentials; they are stored as secrets so they stay out of logs. There is no key to store: Workload Identity Federation lets only jobs running in that GitHub environment act as that environment's deployer.

And at repository level (**Settings > Secrets and variables > Actions > Variables**):

| Name | Value | Effect |
| --- | --- | --- |
| `STAGING_DEPLOY_ENABLED` | `true` | turns on `deploy-staging.yml`; until set, the job is skipped |

For the k6 workflow, optional repository secrets `K6_STUDENT_TOKEN` and `K6_TEACHER_TOKEN`: app tokens of staging demo accounts (never production users).

Protect release tags: **Settings > Rules > Rulesets > New tag ruleset**, target `v*`, restrict creation and deletion to maintainers. Keep `main` protected with the CI checks required.

### 5. First staging deploy

Set `STAGING_DEPLOY_ENABLED=true`, then **Actions > Deploy staging > Run workflow** on `main` (or merge anything). The first deploy migrates the empty database and provisions the admin (`ADMIN_EMAIL` from `env/staging.env`, password in Secret Manager):

```bash
gcloud secrets versions access latest --secret=navigateed-admin-password --project=navigateed-staging
```

Check the smoke job is green, sign in, and confirm the scheduler runs every minute (`gcloud run jobs executions list --job=navigateed-scheduler --region=africa-south1 --project=navigateed-staging --limit=5`).

### 6. Error Reporting notifications

Cloud Console > Error Reporting (in each project) > **Configure notifications**: turn on e-mail for new errors to the alert address. The alert policies created by the script cover uptime, error volume, failed jobs, the scheduler and the worker.

### 7. First production run

Production already runs (`navigateed-admin`, `navigateed-mysql` on `db-f1-micro`, `gs://navigateed-d8c06-admin`). The first run changes the live service, so do it at a quiet time, with a backup and a way back:

1. Back up the database and keep the current service definition:
   ```bash
   gcloud sql backups create --instance=navigateed-mysql --project=navigateed-d8c06 --description="Before first provisioning run"
   gcloud run services describe navigateed-admin --region=africa-south1 --project=navigateed-d8c06 --format=export > navigateed-admin-before.yaml
   ```
2. Compare `navigateed-admin-before.yaml` with `infra/gcp/env/production.env`: the database user (`DB_USERNAME`), the admin e-mail, `APP_URL`, and the uploads mount. Correct the env file where it differs.
3. Read the plan: `ALERT_EMAIL=<address> infra/gcp/provision.sh production --dry-run`.
4. Apply everything except the database restart: `ALERT_EMAIL=<address> CONFIRM_PRODUCTION=yes infra/gcp/provision.sh production`. The panel gets a new revision with its own service account, JSON logs and the database cache; the worker and the scheduler job are created with the sample image until the first production deploy.
5. In a quiet hour, apply the Cloud SQL tier, high availability and point-in-time recovery (the instance restarts for a few minutes): `ALERT_EMAIL=<address> CONFIRM_PRODUCTION=yes ALLOW_SQL_RESTART=yes infra/gcp/provision.sh production`. The disk stays HDD; moving to SSD needs a new instance and is a separate decision.
6. Release the first tag through [release.md](release.md); it deploys the real image to all three roles.

If step 4 breaks the panel: `gcloud run services replace navigateed-admin-before.yaml --region=africa-south1 --project=navigateed-d8c06`.

### 8. DNS and custom domains

- Portals and docs: Firebase console > Hosting > each site > **Add custom domain** (`app.`, `teach.`, and for staging `staging-app.`, `staging-teach.`), then the DNS records it shows.
- Panel and API: Cloud Run domain mappings are not offered in `africa-south1`; use a global external Application Load Balancer with a serverless network endpoint group for `navigateed-admin`, a Google-managed certificate for `admin.navigateed.co.za`, and a Cloud Armor policy (see [wiki Deployment](../../wiki/Deployment.md)). Then set `APP_URL` in the env file, re-run the script (it keeps the `run.app` address in `TRUSTED_HOSTS`), and set `PANEL_URL` in the GitHub environment.
- Mail: the SES records in ADR 0004.

## Secrets

Values never go into the repository, an env file, a workflow or a ticket. To add or replace one:

```bash
read -rs VALUE && printf '%s' "$VALUE" | gcloud secrets versions add <secret-name> --project=<project> --data-file=- && unset VALUE
```

- `navigateed-app-key`: `base64:` followed by 32 random bytes in base64 (`printf 'base64:%s' "$(openssl rand -base64 32)"`). Changing it signs everyone out of the panel.
- `navigateed-db-password`: change the Cloud SQL user's password at the same time (`gcloud sql users set-password <user> --host=% --instance=navigateed-mysql --prompt-for-password`).
- New revisions read `latest`; redeploy (or re-run the deploy workflow) to pick up a new value.
- In production, adding or rotating a secret is the product owner's call (Build Bible section 4).

Secrets still stored in `settings` rows (SMTP, FCM, payment keys) move to Secret Manager in Phase 0 work stream S6; their names will be added to the script and this table then.

## Costs to know about

Cloud SQL is the largest cost (high availability doubles the instance), then the worker (one instance with CPU always allocated) and the panel's warm instance in production. The scheduler job runs 1,440 short executions a day. Uptime checks and log-based metrics stay within the free allowance at this volume. Staging can be scaled down between phases by setting `WORKER_MIN_INSTANCES=0` and pausing the trigger (`gcloud scheduler jobs pause navigateed-scheduler-every-minute --location=africa-south1 --project=navigateed-staging`).
